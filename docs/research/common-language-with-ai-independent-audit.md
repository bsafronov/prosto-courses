## Материальные замечания

### M1. Deprecated Prompt Optimizer представлен как текущий устойчивый пример — исправлено

**Где:**
`modules/metaprompting-i-perenos/lessons/kandidaty-i-otlozhennaya-proverka.mdx:46-49`;
`docs/research/common-language-with-ai-evidence-base.md:443-448`.

Формулировка «текущий OpenAI prompt optimizer» и связанная с ней ссылка не
учитывают объявленное прекращение работы Evals: интерфейс станет read-only
2026-10-31, окончательное отключение назначено на 2026-11-30. Это происходит в
пределах жизненного цикла курса, а `reviewAfter: 2026-11-02` наступает уже после
первого несовместимого изменения. Кроме того, документация требует минимум три
строки данных, каждая из которых имеет результат grader **или** человеческую
аннотацию; утверждение «требует датасет и graders» слишком категорично.

**Исправление:** убрать продуктовую функцию из устойчивого объяснения и оставить
провайдер-независимый процесс
`кандидаты → единый development set → оценивание → ручная проверка → один held-out check`.
Если функция остаётся как лабораторный пример, явно пометить её deprecated,
указать даты прекращения работы и назначить перепроверку не позднее 2026-10-30.
Требование сформулировать точно: «минимум три строки; для каждой — результат
grader или человеческая аннотация; graders рекомендуются для масштабируемой
оценки».

**Основания:** [официальная страница Prompt Optimizer](https://developers.openai.com/api/docs/guides/prompt-optimizer),
[официальный журнал deprecations](https://developers.openai.com/api/docs/deprecations#2026-06-03-evals-platform).

### M2. Архивный пример `seed` используется как актуальная provider-specific документация — исправлено

**Где:**
`modules/ot-namereniya-k-specifikacii/lessons/variativnost-i-povtornye-zapuski.mdx:30-41`;
`docs/research/common-language-with-ai-evidence-base.md:138-151,558`.

Cookbook-страница датирована 2023 годом, помечена как archived и использует
устаревшие preview-модели. Сам технический вывод курса — `seed` не гарантирует
идентичность, качество или истинность — верен, но источник не годится как
подтверждение текущей доступности и семантики параметра. Provider-specific
рекомендация тем самым нарушает собственную Source Policy курса.

**Точная замена основного абзаца:**

> Параметры воспроизводимости зависят от API и модели. Если текущая документация
> выбранной системы поддерживает `seed` или аналогичный параметр, фиксируй его
> вместе с точным `model ID` и существенными условиями, но не считай гарантией
> идентичности, качества или истинности.

Сослаться на текущий справочник выбранного API и рекомендации по evals. Архивный
Cookbook допустим только как явно обозначенный исторический пример. Для OpenAI
добавить оговорку: поддержка и поведение проверяются для конкретного endpoint и
model snapshot; воспроизводимость оценивается тестами, а не выводится из одного
параметра.

**Основания:** [архивная Cookbook-страница](https://cookbook.openai.com/examples/reproducible_outputs_with_the_seed_parameter),
[текущий Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create),
[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

### M3. Совет по правам и деидентификации допускает опасно широкое прочтение — исправлено

**Где:**
`modules/evidence-i-bezopasnost/lessons/privatnost-predvzyatost-i-prava.mdx:35-47`.

Вариант «использовать … собственное резюме» может быть прочитан как автоматическое
право передать или преобразовать защищённый материал. Самостоятельное резюме не
устраняет требования лицензии, договора и применимого права. Соседнее утверждение
о повторной идентификации корректно, но для consequential privacy guidance ему
нужен прямой авторитетный источник. Удаление имени также нельзя без оценки риска
называть анонимизацией.

**Исправление:** заменить вариант действия на:

> Использовать только разрешённый объём и способ обработки; проверить лицензию,
> договор и применимое право. Собственное резюме не создаёт разрешение
> автоматически. Если допустимость неясна — не передавать материал и запросить
> разрешение.

После примера с должностью, городом и датой добавить ссылку на NIST SP 800-188 и
употреблять буквальное «удалены прямые идентификаторы»; не называть данные
анонимными или псевдонимизированными без проверки метода и риска повторной
идентификации. Это глобальный учебный курс, поэтому не следует
давать безусловный вывод из права одной юрисдикции.

**Основания:** [NIST SP 800-188](https://www.nist.gov/publications/de-identifying-government-datasets-techniques-and-governance),
[U.S. Copyright Office: Copyright](https://www.copyright.gov/what-is-copyright/),
[U.S. Copyright Office: Fair Use](https://www.copyright.gov/fair-use/).

## Исправлено во время аудита

### R1. Несовпадение протокола, числа результатов и offline fallback

В исходной редакции урока
`modules/izmerenie-i-uluchshenie/lessons/baseline-i-variativnye-zapuski.mdx`
протокол давал девять результатов (`2 + 3 + 3 + 1`), а текст называл восемь;
задание также запрашивало случай, которого не было в предоставленной offline
серии. Это делало детерминированный ответ противоречивым и обязательный offline
маршрут неполным.

Текущая редакция исправлена корректно: строки 55–60 задают девять результатов,
строки 78–81 говорят о `3 из 9`, а строки 115–120 повторяют тот же доступный
offline протокол. Результат независимого пересчёта: девять наблюдений; три ошибки
в рискованных генеративных случаях. Процент намеренно не выводится: малая
стратифицированная выборка не является оценкой общей частоты ошибок.

## Незначительные замечания

### N1. Сузить формулировку о гарантии JSON Schema

В evidence base (`:85-89`, `:561`, `:625-628`) «schema mode гарантирует структуру»
звучит шире официальной области применимости. Структурированный вывод может дать
refusal, incomplete response или ошибку, а поддержка ключевых слов схемы
ограничена. Урок для ученика уже в основном проводит правильную границу между
формой и истинностью.

**Исправление:** «для успешного, не-refusal ответа с поддерживаемой схемой API
может обеспечить соответствие схеме; refusal, incomplete и ошибки обрабатываются
отдельно; значения всё равно валидируются».

**Источник:** [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

### N2. Обновить канонические URL provider-документации

- В privacy-уроке `:57` и evidence base `:424` заменить redirect на
  `https://developers.openai.com/api/docs/guides/your-data#default-usage-policies-by-endpoint`.
- В `perenosimoe-yadro-i-usloviya-zapuska.mdx:64` заменить redirect на
  `https://developers.openai.com/api/reference/overview#backwards-compatibility`.

Смысл privacy-урока верен. Можно дополнительно назвать важные границы ZDR:
допуск организации, совместимость endpoint/model/tool, application state,
сторонние сервисы, регион и договор.

### N3. Не заявлять неподтверждённый приоритет исследования

В `prompt-injection-kak-granica-doveriya.mdx:44` заменить «Первая работа» на
«Ранняя работа». Статья действительно демонстрирует indirect prompt injection,
но приоритет «первая» не нужен для учебного вывода и не подтверждён приведённым
источником.

### N4. Пометить OWASP Top 10 как версионный архив

Ссылка в `prompt-injection-kak-granica-doveriya.mdx:48-51` сейчас ведёт в архив.
Сохранить источник можно как «архивная версия OWASP Top 10 for LLM Applications
2025» либо заменить на текущую каноническую страницу и проверить номер категории.
Учебный тезис о prompt injection и многоуровневой защите от этого не меняется.

## Проверено без замечаний

- Модель описана как вероятностный генератор без антропоморфной гарантии знания.
- Иерархия инструкций и отсутствие полномочий у цитированного/загруженного текста
  согласуются с Model Spec; курс не обещает полного соответствия конкретной
  production-модели спецификации.
- Prompt injection корректно показан как граница доверия; разделители не названы
  самостоятельной защитой; внешние действия требуют минимальных прав и
  подтверждения.
- Урок о структурированном результате отделяет синтаксическую форму от истинности
  значений.
- Русский и английский не ранжируются универсально; перенос предлагается проверять
  на одном наборе.
- Детерминированные KnowledgeCheck имеют однозначные ответы из локального
  контракта. Арифметика проверена независимо: `15 × 6 500 + 48 000 = 145 500 ₽`;
  `4 × 3 = 12` результатов; `3 × 3 = 9` результатов; `5 из 9` в соответствующем
  примере.
- Worked examples не скрывают известные ответы и не требуют сетевого доступа для
  обязательного маршрута.
- Capstone покрывает восемь outcomes, содержит privacy/injection/action-gate
  критерии и не подменяет рубрику непрозрачным итоговым баллом.
- Термины на русском в целом последовательны; англоязычные термины определяются
  при первом значимом употреблении.

## Итоговая проверка после исправлений

- M1: устойчивое объяснение теперь использует провайдер-независимый цикл
  `кандидаты → development set → оценивание → ручная проверка → held-out check`;
  deprecated Prompt Optimizer удалён из учебного основания.
- M2: архивная Cookbook-ссылка удалена; текст требует сверять поддержку
  параметра по конкретным API, endpoint и модели и не обещает идентичность.
- M3: собственное резюме больше не названо автоматическим основанием для
  обработки; добавлены границы лицензии, договора, применимого права и
  NIST SP 800-188; удаление прямых идентификаторов не названо анонимизацией или
  псевдонимизацией.
- R1: девять результатов и обязательный offline-протокол независимо пересчитаны
  повторно; условие и доступные данные совпадают.
- N1–N4: область гарантии schema mode сужена, provider URLs обновлены,
  исследовательский приоритет смягчён, OWASP 2025 явно помечен архивом.

Независимый эксперт и целевой пользователь не участвовали. Это независимый
ИИ-аудит, а не independent expert review, certification или доказательство
отсутствия ошибок.
