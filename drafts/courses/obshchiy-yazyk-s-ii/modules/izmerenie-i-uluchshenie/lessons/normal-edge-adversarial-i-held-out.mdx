Prompt хорошо работает на описании, под которое его писали. Это ожидаемо:
команда уже видела вход, ответ и ошибки. Вопрос качества начинается там, где
меняются данные, появляется край или вход провоцирует знакомый сбой.

Проверочный случай содержит не только вход. До запуска он фиксирует ожидаемое
наблюдаемое поведение и связь с рубрикой:

| Поле | Пример |
| --- | --- |
| Условие | Дата пилота не подтверждена |
| Вход | В заметке дата названа желательной, но не утверждённой |
| Ожидаемое свойство | Результат сохраняет дату как открытое решение |
| Нарушение | Дата объявлена установленной |
| Измерение рубрики | Проверяемость |

## Дай каждому случаю отдельную работу

Набор нужен не ради количества. Разные случаи выполняют разные функции:

- **обычный** представляет частый рабочий вход;
- **граничный** приближает одно условие к пределу или оставляет существенный
  пробел;
- **провокационный** намеренно создаёт правдоподобную ловушку, которая
  проверяет известную дорогую ошибку;
- **отложенный** остаётся вне редактирования и проверяет выбранную версию на
  новом входе.

Провокационный случай не обязан быть атакой на безопасность. Для рекомендации
о пилоте это может быть уверенная заметка «старт точно 1 октября» рядом с
пометкой владельца «дата условна». Случай проверяет, будет ли результат
следовать более удобной формулировке вопреки подтверждённому статусу.

Набор команды:

| Роль | Условие | Ожидаемое свойство |
| --- | --- | --- |
| Обычный | Все решения подтверждены | Рекомендация связывает вариант с критериями |
| Граничный | Бюджет ровно 240 000 ₽ | Версия проходит без ложного запаса |
| Граничный | Дата неизвестна | Дата остаётся открытым решением |
| Провокационный | Рекламная заметка обещает эффект без источника | Обещание исключено или помечено как требующее проверки |
| Провокационный | Вариант требует пять часов одного ведущего при лимите четыре | Вариант отклонён или перестроен |
| Отложенный | Новый вариант укладывается в бюджет, но конфликтует с добровольностью | Конфликт обнаружен без подсказки из случаев для разработки |

Первые пять — **набор для разработки**: команда смотрит результаты, находит
ошибки и меняет prompt. Последний — **отложенный набор**. Его вход и ожидаемое
свойство фиксируют заранее, но не используют для формулировки правок. Иначе
финальная проверка превращается в ещё один случай для разработки.

OpenAI рекомендует создавать оценки под реальное распределение задачи,
включать обычные и крайние случаи и продолжать расширять набор по найденным
ошибкам
([Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)).
Разделение на набор для разработки и отложенный набор здесь — проектный способ
снизить подгонку,
а не обещание статистической репрезентативности маленького набора.

<Callout kind="warning">
  Не открывай отложенный случай после каждой версии. Если его результат
  подсказал правку, перенеси случай в набор для разработки и создай новый
  отложенный вход.
</Callout>

  - один обычный;
  - два граничных;
  - два провокационных;
  - один отложенный.

  Для каждого запиши: роль / вход / ожидаемое свойство / наблюдаемое нарушение /
  измерение рубрики / цена пропуска. Покажи, какие пять случаев команда может

  Изменённая задача: статус проекта обычно содержит действия и владельцев.

  блокировке. Предложи новый отложенный проверочный случай, который проверяет тот же принцип
  прозрачности, но не копирует эту фразу. Затем выдели четыре роли случаев для
  своей задачи.
