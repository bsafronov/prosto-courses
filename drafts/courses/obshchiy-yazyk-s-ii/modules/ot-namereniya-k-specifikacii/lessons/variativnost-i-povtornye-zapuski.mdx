Один запуск дал аккуратный план курса. Второй по тому же запросу пропустил
условие о бюджете. Какой ответ показывает «настоящее» поведение prompt?

Оба. Prompt — инструкция и данные, переданные модели, — задаёт условия
генерации, но не единственный неизбежный текст. Проверять нужно не лучший
скриншот, а результаты на важных случаях и, когда вариативность влияет на
решение, в нескольких запусках.

## От одного ответа перейди к распределению наблюдений

В выбранной генеративной системе повтор одного входа может дать разные ответы.
Точное поведение зависит от модели, интерфейса и условий запуска. Например,
даже фиксированный `seed` в конкретном OpenAI API описывается как механизм с
ограниченной воспроизводимостью, а не гарантия идентичного
или правильного результата
([OpenAI Cookbook, Reproducible outputs](https://cookbook.openai.com/examples/reproducible_outputs_with_the_seed_parameter)).
Температура влияет на выбор токенов, но значение `0` не превращает текст в
проверенный факт и не гарантирует одинаковое поведение всех моделей. Некоторые
провайдеры отдельно предупреждают, что рекомендации по параметрам зависят от
семейства модели
([Google, Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies),
[Gemini model guidance](https://ai.google.dev/gemini-api/docs/latest-model)).

Поэтому отделяй три вопроса:

1. **Вариативность.** Меняется ли наблюдаемое свойство между запусками?
2. **Качество.** Соответствует ли каждый результат заранее заданному критерию?
3. **Истинность.** Поддержан ли фактический тезис внешним свидетельством?

Низкая вариативность может стабильно повторять ошибку. Высокая вариативность
может давать несколько приемлемых формулировок. Температура отвечает только за
часть первого вопроса и не решает два остальных.

### Реши, когда повторять

Не каждой задаче нужны десятки запусков. Масштаб проверки зависит от того,
может ли различие изменить решение и какова цена незамеченной ошибки.

| Ситуация | Разумная первая проверка | Почему |
| --- | --- | --- |
| Придумать пять неокончательных названий для внутреннего черновика | Один запуск и быстрая проверка ограничений | Варианты ожидаемы, цена ошибки мала |
| Извлечь даты и владельцев из заметок | Несколько разных проверочных случаев; точные поля проверить по исходнику | Ошибка способна потеряться за беглой формой |
| Выбрать план запуска по неполным данным | Несколько случаев и повторных запусков на рискованных случаях | Разные допущения способны изменить решение |

Перед изменением prompt команда фиксирует **baseline** — исходные результаты в
записанных условиях. Без них новая версия не с чем сопоставлять. Для первого
baseline плана запуска команда берёт три случая:

- обычное описание задачи с полными датами;
- описание без владельца одного решения;
- описание с конфликтующими ограничениями бюджета и срока.

Критерий один: ответ не должен превращать неизвестное в установленный факт.
На обычном случае достаточно одного пробного запуска. На двух рискованных
команда делает по три: именно там вариативность может скрыть ошибку. Это не
универсальная статистическая норма, а прозрачный стартовый протокол. Больше
случаев или запусков может изменить вывод.

<Callout kind="key">
  Повторный запуск полезен только рядом с критерием. Без критерия несколько
  ответов превращаются в выбор понравившегося текста, а не в проверку.
</Callout>

Теперь у тебя есть причина не доверять одному красивому ответу. Следующий риск
похож: большой текст формально помещается в контекстное окно, но важное условие
может не повлиять на результат.
